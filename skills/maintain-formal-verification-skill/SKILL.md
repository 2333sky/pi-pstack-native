# Maintain a formal verification skill

A formal check proves a property of what it describes. When the code changes and the verification does not, the check can keep passing on code that no longer exists. That pass looks like a proof, but the description is stale.

Use this to maintain a verify skill generated by `/skill:create-formal-verification-skill`, or any project-local skill that runs a model checker, prover, or code-level verifier against named code. The project-local skill handles changes made while an agent uses it. This skill handles changes that skipped it, including merges, edits made without the skill, and drift across many commits.

## Outcomes

Give each check one outcome, and say which:

- **in sync**. No change since the last sync alters what the check describes, and the check passes.
- **updated**. The code changed, the verification now describes the new code, and the check passes.
- **bug**. The verification describes the current code, and the code breaks the property. This is a finding about the code. It is not drift.
- **blocked**. The check could not be brought back in line or could not run. Say exactly why.

A check can be both updated and bug. The update makes the verification describe the code again, and then the property fails on it.

## Edit scope

Edit only the verification. This includes models, harnesses, property files, and the verify skill itself. Never edit product code during a run unless the user asks you to. When a property fails on the current code, do not weaken the property or the model to make it pass. Report the failure.

## Tool availability

This package has no verified formal-tool runner. Use the tool and exact commands recorded in the project's verify skill. Do not substitute a runtime test for a formal check.

- Check Git with `git --version`. If Git or the sync history is unavailable, report the affected checks as blocked.
- For a verifier executable found through the shell, set `verifier` to the executable named by the verify skill. Run `command -v "$verifier"` to check its installation. Then run the skill's documented availability check, if any, and its exact verification command.
- For a project-local harness or another launch method, run the install check recorded in the verify skill. Do not invent an executable, path, version flag, or setup command.
- If the tool is missing, its install check fails, or the skill provides no usable tool command, report the check as blocked. Name the missing tool or command and give the exact install check that failed. If no install check is documented, state that gap. Never claim a tool result without running it.

`/skill:create-formal-verification-skill` requires that skill to be installed and loaded in Pi. If it is unavailable when needed, report that blocker. Do not substitute `/skill:create-verification-skill`, which checks runtime behavior instead.

## Pass

1. **Find the checks.** A verify skill has no fixed name. Find project skills that run a model checker, prover, or another verifier against named code. Read each one you find, or the one the user named. For each check, collect the property, the code it covers, the bounds and assumptions, the run command, and the commit where it was last confirmed to describe the code. If no verify skill exists, stop and point at `/skill:create-formal-verification-skill`. If the skill records no sync commit, use the last commit that changed the verification files. Say that you did.

2. **Run it as it is.** Run each check once before changing anything. Record the result. A pass does not show that the code is correct. It shows that the old description still holds. A failure can be drift or a bug. Do not decide which until step 5.

3. **Read every change to covered code.** Diff the covered files from the sync commit to the current commit. Read each commit message. Track covered functions that were renamed, split, or moved to another file. Look for new code that touches the guarded state, such as a function that writes the same fields. Put each change in one of these categories:
   - **No effect.** The change does not alter what the verification describes. Examples include formatting, comments, and uncovered code paths. Check this against the model or harness, not the commit message.
   - **The verification no longer describes the code.** An indivisible action became two steps, a branch was added or removed, a check moved, a new path reaches the guarded state, or a value has a different range. Change the model or harness.
   - **The promise changed on purpose.** The code's promise changed, and the doc comment, tests, changelog, or commit message shows that this was intended. Change the property and cite that evidence.
   - **The promise may be broken.** The code changed, and no evidence says the promise changed. Treat a failure that follows as a bug candidate.

4. **Update from the code, not from the result.** Change the model or harness so each changed part points to code a reviewer can open. Keep one indivisible code step as one verification step. Write the update from the code before rerunning. Do not shape it to make the check pass. Change a property only when the promise changed on purpose. Record its old wording, new wording, and evidence. Keep the bounds unless the code change makes them wrong. Report any bound you must reduce.

5. **Rerun and judge each result.**
   - **Pass.** A passing description may have lost the ability to fail. Break the new code in the way the property guards against. For example, remove a new check or reorder a new step. Confirm that the check catches the break. Then drop the break.
   - **Fail.** Replay the counterexample against the real code, step by step. If a step cannot happen in the code, the verification is wrong. Fix the verification and say what was wrong. If every step can happen, it is a bug. Name the commit that introduced it. Tell the counterexample as steps in the code's own words. State the harm in one sentence. If a cheap test or reproduction against the real code shows the bug, include it as report evidence. Do not commit it to product code.

6. **Update the verify skill.** Update the covered code, commands, bounds, assumptions, and sync commit. Set the sync commit to the commit you checked. Do not move the sync commit for a blocked check. Say so in the report. Then follow the verify skill once as the next agent would. Confirm that its steps still run.

## Report

Tell the user, for each check:

- the outcome, and the commits you read;
- what changed in the verification and why. Give a short reason for each change. State whether the code changed shape or the promise changed on purpose. Include evidence for a changed promise;
- the rerun result, and the break used to show the updated check can still fail;
- each bug in plain words. Give the counterexample as steps in the code's words, the harm, and the commit that introduced it;
- what the verification still does not cover, including new code it should cover but does not.

Say which failures were drift in the verification and which were code bugs. If a check passed before the update and fails after it, say that the old pass was on a stale description.

Put verification updates in a change of their own, separate from any product fix.
